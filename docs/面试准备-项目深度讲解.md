# TraceCoder 项目深度讲解 —— 面试准备文档

> 基于本地源码逐模块拆解，覆盖架构、核心机制、安全设计、评测体系，附面试话术与高频问答。

## 一、项目概述

### 1.1 项目定位

TraceCoder 是一个**本地代码仓库的交互式 Coding Agent**，核心解决大模型写代码 Agent 的四大工程痛点：

| 痛点 | 解决方案 |
|------|---------|
| 长任务上下文爆炸，token 暴涨 | L1-L4 分级上下文压缩 |
| 程序崩溃会话状态全部丢失 | append-only JSONL 事件溯源 + 事件回放恢复 |
| Agent 随意读写本地文件，误删覆盖代码 | 三级权限策略 + 路径沙箱 + 写前 diff 预览 + SHA256 快照校验 |
| 不同大模型 API 格式不统一，评测难搭建 | ChatProvider 统一抽象 + Harbor Docker 隔离评测 |

### 1.2 技术栈

- **Python**：主体开发语言
- **AnyIO**：异步 IO 库，处理异步模型调用、超时取消
- **Textual**：终端 UI 框架，交互式控制台界面
- **MCP**：Model Context Protocol，外部工具集成标准协议
- **pytest**：单元测试
- **Harbor**：基于 Docker 的 Coding Agent 评测运行时

### 1.3 项目结构

```
tracecoder/
├── agent/          # Agent 核心运行时（loop、tool_execution、subagent、background）
├── app/            # Textual TUI 终端界面
├── context/        # 会话上下文、JSONL 存储、压缩、检查点
├── planning/       # 任务计划（TaskPlan DAG/线性、revision 乐观锁）
├── permissions/    # 权限策略、授权管理、路径沙箱
├── providers/      # 大模型适配器（OpenAI 兼容、Anthropic）
├── tools/          # 内置工具（文件操作、git、shell、写前预览等）
├── mcp/            # MCP 协议工具集成
├── runtime/        # 运行时基础设施（取消令牌、事件总线）
└── session/        # 会话创建、恢复、目录管理
```

## 二、整体架构

```
用户输入
  ↓
AgentLoop（agent/loop.py）← 核心调度引擎
  ↓ 每轮调用前
ContextWindowManager（context/manager.py）← L1-L4 上下文压缩编排
  ↓
ContextBuilder（context/context_builder.py）← 投影成 provider messages
  ↓
ChatProvider（providers/base.py）← 统一模型接口
  ↓ 返回 tool_calls
ToolExecutor（agent/tool_execution.py）← 工具执行调度
  ↓ 每个工具执行前
PermissionManager（permissions/manager.py）← allow/ask/deny 三级决策
  ↓ 写操作额外经过
PrewriteReview（tools/review.py）← diff 预览 + SHA256 快照校验
  ↓
JsonlSessionStore（context/store.py）← append-only 事件落盘
```

所有交互事件全部写入 `sessions/{session_id}.jsonl`，这是整个系统的**唯一事实来源**。

## 三、Agent 主循环（loop.py）

### 3.1 一轮用户请求的完整生命周期

入口是 `run_user_turn()`，同步走 `_run_user_turn_sync_impl()`，流式走 `_run_user_turn_streaming_impl()`。

核心步骤：

1. **检查挂起状态**：如果上一轮卡在权限确认，直接返回 pending，不追加新用户消息
2. **校验附件**：图片需要模型声明视觉能力
3. **开始一轮**：重置 telemetry、停滞检测、完成校验门等
4. **修复中断的 tool_call**：上次崩溃可能留了 assistant tool_call 没有 tool_result，补写 interrupted 结果
5. **写入用户消息**：`append_user_message()` 写入 JSONL
6. **任务边界分类**：判断是否新任务，是则触发上下文压缩
7. **进入工具循环**：`_run_tool_loop_interactive()`

### 3.2 工具循环的核心逻辑

`_run_tool_loop_interactive()` 是整个 Agent 的心脏，退出条件只有三类：
- 模型返回的 response 没有 tool_calls → 最终回答
- 命中 max_tool_rounds → 防止无限循环
- 某个工具需要用户输入/权限确认 → 暂停

核心伪代码：

```python
response = complete_once(tool_choice="auto")  # 第一次问模型

while response.tool_calls:
    # 关键顺序：必须先写 assistant tool_call，再写 tool_result
    # 这样 provider 后续才能看到合法的 "assistant(tool_calls) -> tool(result)" 序列
    self.session.append_assistant_response(response)

    execution = self.tool_executor.execute_interactive(response.tool_calls)
    if execution.pending_input is not None:
        return response, execution.pending_input  # 暂停等用户

    tool_rounds += 1
    if tool_rounds >= max_tool_rounds:
        break  # 轮次上限

    response = complete_once()  # 把工具结果回喂给模型，继续问
```

**关键设计**：必须先 `append_assistant_response(response)`（含 tool_calls），再执行工具并 `append_tool_result`，保证 provider 看到的永远是 assistant→tool 的合法序列。这就是"严格保证 tool_call 和 tool_result 配对顺序合法"的具体实现——不是靠校验，而是靠写入顺序的硬约束。

### 3.3 鲁棒性防护（8 层）

| 防护机制 | 实现 | 具体做法 |
|---------|------|---------|
| **工具轮次上限** | `AgentLoopLimits.max_tool_rounds` | 防止模型无限调用工具死循环 |
| **Provider 调用上限** | `max_provider_calls` | 每次调用前 `_reserve_provider_call()` |
| **单轮超时** | `max_turn_seconds` | `_check_turn_timeout()` 用 `time.monotonic` 计时 |
| **Provider 重试** | `provider_retry.py` | `_complete_once_with_recovery()` 对可重试错误指数退避 |
| **Prompt 过长恢复** | `requires_compaction` | Provider 报 context 过长时，触发压缩后重试一次 |
| **中断修复** | `_repair_interrupted_tool_calls_before_provider_request()` | 每次请求前检查悬挂的 tool_call，补写 interrupted 结果 |
| **停滞检测** | `StagnationGuard` | 检测模型反复调用相同工具无进展，注入 guidance |
| **完成校验门** | `ExecutionEvidence` + `completion_gate` | 模型说做完后，用执行证据判断是否真的改了代码/跑了测试 |

**面试话术**：
> "主循环不是简单的 while 循环，我们做了 8 层防护：轮次上限、调用上限、超时、API 重试、上下文过长自动压缩恢复、中断修复、停滞检测、完成校验门。这些都是实际跑长任务时踩坑踩出来的。"

## 四、会话持久化与恢复

### 4.1 append-only JSONL 存储

核心代码（`context/store.py`）：

```python
class JsonlSessionStore:
    def append_event(self, event: SessionEvent) -> None:
        path = self._session_path(event.session_id)
        with path.open("a", encoding="utf-8") as file:
            file.write(json.dumps(event.to_dict(), ensure_ascii=False, sort_keys=True))
            file.write("\n")
        SessionIndex(self.root).update_event(event)
```

**为什么用 JSONL 而不是 JSON？**
- JSON 是整体读写，修改要重写整个文件，崩溃时可能写坏
- JSONL 一行一个事件，只追加（`"a"` 模式），就算写到一半崩溃，最多坏最后一行，历史事件完好
- 人可以直接打开看，调试方便
- 接口设计上预留了换存储引擎的能力（后续可迁移 SQLite）

### 4.2 事件回放恢复

```python
def rebuild_session_view(self, session_id: str) -> SessionView:
    view = SessionView(session_id=session_id)
    for sequence, event in enumerate(self.list_events(session_id), start=1):
        self._apply_event(view, event, sequence=sequence)
    return view
```

支持的事件类型：
- `session_created` / `session_metadata_updated` → 更新元数据
- `checkpoint_created` → 追加检查点
- `compaction_completed` → 应用压缩替换
- `message_part_metadata_updated` → 更新消息 part 元数据
- `task_plan_updated` → 更新任务计划（带 revision 链校验）
- `user_message` / `assistant_message` / `tool_result` → 追加消息

### 4.3 会话恢复入口

```python
def resume(self, session_id: str) -> ResumeResult:
    validate_session_schema(self.store, session_id)  # 校验 schema 版本
    record = require_usable_record(catalog.get_session(session_id))
    session = bootstrap.resume(session_id)  # 从 JSONL 重建整个 session
    session.restore_pending_permission_execution()  # 恢复挂起的权限确认
    return ResumeResult(session=session, record=record)
```

恢复时还会做 schema 版本校验，旧版本的事件日志和当前 runtime 不兼容时直接报错，不会静默回放产生错误状态。

**面试话术**：
> "所有事件都在 JSONL 里。恢复时逐事件回放重建内存中的 SessionView。如果上次卡在权限确认，从 JSONL 里恢复 pending_permission_execution 状态（包括原始 tool_call 的深拷贝，不信任 UI 回传的参数），直接继续等用户确认，不需要重新走一遍模型。"

## 五、上下文压缩 L1-L4

### 5.1 整体编排

`ContextWindowManager.compact_if_needed()` 是编排入口：

```
触发判断（双水位线 high/low watermark）
  → 高水位线触发？熔断器开？上次压缩无效果？→ 跳过
  → L1-L3 程序化压缩（CompactionPipeline.compact）
    → 达到目标 token？→ 成功返回
    → 没达到？→ L4 LLM 摘要压缩
      → 生成候选 → 校验 tool 序列合法性 → 校验 token → commit checkpoint
      → 失败？→ fallback 策略（更强程序化压缩 / 更强 L4 摘要重试）
```

### 5.2 L1：旧任务对话裁剪

只裁剪可以安全遗忘的旧任务普通对话：
- 跳过最新用户消息
- 跳过带 tool_call 的 assistant 消息（不能破坏工具事务）
- 只处理属于"旧任务"的 part（通过 task_hash 判断）
- 只处理"冷"的 part（距离当前轮次 >= 8 轮）

**核心约束**：绝对不碰带 `tool_call` 的 assistant 消息——那是 provider 可见的工具事务的一部分，裁了就会破坏 `tool_call → tool_result` 的配对。

### 5.3 L2：按内容类型路由压缩

针对**已被消费的工具结果**，按内容类型走不同的压缩器：

| 内容类型 | 压缩器 |
|---------|--------|
| BUILD_OUTPUT | BuildOutputRouteCompressor |
| GIT_DIFF | GitDiffRouteCompressor |
| HTML | HtmlRouteCompressor |
| JSON_ARRAY / JSON_OBJECT | JsonRouteCompressor |
| SEARCH_RESULTS | SearchResultsRouteCompressor |
| SOURCE_CODE | SourceCodeRouteCompressor |
| PLAIN_TEXT | PlainTextRouteCompressor |

L2 压缩前会先把原始内容**归档**（`archive.store_original`），生成 `archive_id`，后续可通过 `retrieve_archive` 工具找回。压缩后的 part 元数据记录：
- `archive_id`：归档 ID
- `original_content_sha256`：原始内容哈希（完整性校验）
- `original_tokens` / `replacement_tokens`：压缩前后 token 数

### 5.4 L3：工具结果归档占位

L3 是更激进的压缩，把工具结果直接替换成**占位符**，只保留摘要和关键错误信息。

**L3 不调 LLM**，"摘要"是从工具结果的结构化 metadata 里用固定模板拼出来的纯文本。核心代码（`context/archive.py`）：

```python
def make_placeholder(self, part, record, lifecycle="derived", summary=None, key_errors=()):
    tool_name = part.metadata.get("tool_name")
    status = "success" if part.metadata.get("ok") else "failed"
    resolved_summary = summary or f"Large {tool_name} result ({original_tokens} tokens)"
    errors = key_errors[:3]  # 最多3条错误

    lines = [
        "[Tool result archived]",
        f"archive_id={record.archive_id}",
        f"tool={tool_name}",
        f"status={status}",
        f"lifecycle={lifecycle}",
        f"original_tokens={record.original_tokens}",
        f"summary={resolved_summary}",
    ]
    lines.extend(f"key_errors={error}" for error in errors)
    lines.append("Use retrieve_archive(archive_id, ...) to inspect the original.")
    content = _fit_placeholder(lines, maximum=480)  # 硬限制 480 字符
```

**每一行的来源**：

| 字段 | 来源 | 是否 LLM 生成 |
|------|------|--------------|
| `tool` | `part.metadata["tool_name"]` | 否，原始数据 |
| `status` | `part.metadata["ok"]` | 否，原始数据 |
| `lifecycle` | `tool_lifecycle.py` 分类 | 否，纯规则分类 |
| `original_tokens` | 归档时算的 token 数 | 否，计算出来的 |
| `summary` | `f"Large {tool_name} result ({tokens} tokens)"` | **否，字符串拼接** |
| `key_errors` | `part.metadata.get("error")` | 否，原始数据 |
| `archive_id` | 内容哈希前 32 位 `ar_{sha256[:32]}` | 否，算出来的 |

**模型看到占位符后**：如果需要看原始内容，调用 `retrieve_archive` 工具传入 `archive_id`，就能从归档里把完整原始内容取回来。这是**按需检索**设计：平时上下文里只放 480 字符的"目录卡片"，需要时再加载完整内容。

**L3 触发条件**基于工具结果的**生命周期状态**（`ToolResultLifecycle`）：

| 生命周期 | 含义 | L3 优先级 |
|---------|------|----------|
| `DUPLICATE` | 重复结果（内容 SHA256 完全相同） | 0（最高，必须清理） |
| `SUPERSEDED` | 被后续更大范围的读取取代 | 1 |
| `STALE` | 读取的文件被后续写操作修改了 | 2 |
| `DERIVED` | 派生结果（超过单条 token 预算时） | 3-4 |

生命周期分类是纯规则的（`tool_lifecycle.py`）：
- `view`/`read_multi` 读取文件 → `FRESH`（保留）
- 后续对同一文件有更大范围读取 → 之前的标记 `SUPERSEDED`
- 后续对同一文件有写操作 → 之前的读取标记 `STALE`
- 其他工具（grep/shell 等）→ `DERIVED`
- 内容 SHA256 完全相同的 DERIVED 结果 → `DUPLICATE`

**安全边界**：归档是 all-or-nothing 的，如果持久化或校验失败，保留原始 part，不做压缩。

### 5.5 L4：LLM 摘要 + Checkpoint

L1-L3 都是**程序化**压缩（不调大模型），L4 才调大模型做深度摘要。流程：

1. `l4_service.generate_candidate()` → 调 LLM 生成摘要候选
2. 校验：把 checkpoint 加入 view 后重新估算 token，确认降到目标以下
3. **关键校验**：检查 `InvalidCheckpointBoundaryError`（边界不合法）和 `InvalidToolCallSequenceError`（工具调用序列不合法）
4. `commit_candidate()` → 写入 `checkpoint_created` 事件
5. `store.rebuild_session_view()` → 从 JSONL 重建验证

**Checkpoint 数据结构**：

```python
@dataclass
class Checkpoint:
    id: str
    session_id: str
    summary: str                    # 旧历史的 LLM 摘要
    tail_start_message_id: str      # recent tail 从哪条消息开始
    covered_until_message_id: str   # 摘要覆盖到哪条消息
    source_fingerprint: str         # 输入指纹（防重复压缩）
    strategy_version: str           # 策略版本（兼容性校验）
```

**面试话术**：
> "L1-L3 是程序化压缩，不调模型，快且确定；L4 才调 LLM 做深度摘要生成 checkpoint。每一级压缩后都校验 tool_call/tool_result 序列合法性，L4 提交后还要从 JSONL 重建验证。整个压缩链路有 fallback 策略：L4 失败就退到更强的 L2/L3，再失败就用更强的 L4 摘要重试。"

## 六、权限与安全沙箱

### 6.1 三级决策

`DefaultPermissionPolicy.decide()` 按操作类型分发：

```python
def decide(self, request, *, mode):
    if mode == BYPASS:
        return allow  # bypass 模式全放行（benchmark 用）

    if request.action in {READ_PATH, WRITE_PATH, DELETE_PATH}:
        return self._decide_path(request, mode)
    if request.action == READ_ENV:
        return self._decide_env(request)
    if request.action == GIT_OPERATION:
        return self._decide_git(request)
    if request.action == EXECUTE_SHELL:
        return self._decide_shell(request, mode)
    if request.action == NETWORK_REQUEST:
        return ask  # 内网/本机额外提示
    if request.action == MCP_TOOL:
        return ask
```

### 6.2 路径权限的硬边界

```python
def _decide_path(self, request, *, mode):
    inside_root = all(self._is_inside_project(target) for target in targets)
    sensitive = any(self._is_sensitive_path(target) for target in targets)

    # 读取：项目根内非敏感文件 -> allow；否则 ask
    if action == READ_PATH:
        if inside_root and not sensitive:
            return allow
        return ask

    # 写入：根外 -> ask；敏感文件 -> ask；激进模式根内普通文件 -> allow
    if action == WRITE_PATH:
        if not inside_root:
            return ask
        if sensitive:
            return ask
        if mode == AGGRESSIVE:
            return allow
        return ask

    # 删除：根外 -> 直接 deny（硬边界！）；根内 -> ask
    if action == DELETE_PATH:
        if not inside_root:
            return deny("拒绝删除项目根目录外路径")
        return ask
```

**敏感路径检测**：`.git` 目录、`.env` 文件、`.pem`/`.key` 后缀文件。

**环境变量硬边界**：包含 `KEY/TOKEN/SECRET/PASSWORD/COOKIE` 的环境变量，**直接 deny**，不允许读取明文。

### 6.3 Shell 命令防护

```python
def _decide_shell(self, request, *, mode):
    # 包含 && || $( ; | < > ` 等控制符 -> ask
    if _has_shell_control_operator(command):
        return ask

    if mode == AGGRESSIVE and cwd 在项目根内:
        # 危险命令前缀（rm/sudo/curl/wget/chmod/pip 等）-> ask
        if _is_dangerous_shell_command(command):
            return ask
        # 白名单命令（pytest/ruff/mypy/git status 等）-> allow
        if _is_aggressive_allowed_shell_command(command):
            return allow
    return ask
```

### 6.4 权限管理器

`PermissionManager` 组合了**长期授权（grants）**和**默认策略（policy）**：

```python
def preflight(self, request):
    request = self.normalize_request(request)
    grant_decision = self.grants.matching_decision(request)
    if grant_decision is not None:
        return grant_decision  # 命中长期授权直接返回
    return self.policy.decide(request, mode=self.mode)  # 否则走默认策略
```

用户确认时的选项：
- `Deny`（拒绝）
- `Allow once`（仅本次允许）
- `Allow always`（同范围长期授权）→ 写入 `PermissionGrantStore`

**安全设计**：用户确认后，**重新跑一次预检**，防止调用方误把硬拒绝的请求送进确认流程后创建了 allow always grant。

## 七、工具执行与写前预览

### 7.1 工具执行调度

`ToolExecutor.execute_interactive()` 的执行策略：

1. **顺序执行**为默认
2. **只读工具可并行**：`ls/view/grep/glob/tree/read_multi/git_status/git_diff/git_log`，用 `ThreadPoolExecutor` 并行
3. 遇到需要用户输入的工具 → 暂停，剩余工具跳过
4. 权限放行后才允许转入**后台执行**（`run_in_background`）
5. 后台 coder 角色必须在 **git worktree 隔离**中执行，不碰父工作区

### 7.2 Prewrite Review —— diff 预览 + 快照校验

这是项目最硬核的安全设计。支持的工具：`write`、`edit`、`apply_patch`、`delete`。

**构建预览**：在真正写入前，先 dry-run 计算出每个文件的：
- `before_digest` / `after_digest`：SHA256 哈希
- `diff`：unified diff（用 Python 标准库 `difflib.unified_diff`）
- `added_lines` / `removed_lines`：增删行数
- `snapshot`：`(路径, 当前 SHA256)` 元组

**快照校验**（`is_current` 方法）：

```python
def is_current(self, root, *, access=None):
    sandbox = PathSandbox(root, access=access)
    for review_file in self.files:
        for path, expected_digest in review_file.snapshot:
            target = _snapshot_path(sandbox, path)
            actual_digest = _path_digest(target)
            if actual_digest != expected_digest:
                return False  # 文件被外部改动过！
    return True
```

**在权限恢复时校验**：

```python
if pending.prewrite_review.is_current(project_root, access=sandbox_access):
    return None  # 快照一致，允许执行
return make_prewrite_review_stale_result(...)  # 快照过期，拒绝执行
```

**目录删除的快照**：对目录递归计算所有文件的相对路径 + 内容哈希，确保整个目录树没被外部改动。

**为什么需要 snapshot**：Agent 生成预览（"我要把 foo.py 第 5 行从 A 改成 B"）和用户点确认之间，可能隔了几秒。这几秒里你可能在 VSCode 里手动改了 foo.py。如果 Agent 不管不顾直接写，就会**覆盖你的修改**。snapshot 就是防止这个：确认后先检查文件指纹变没变，变了就拒绝，让 Agent 重新读文件再生成补丁。

**面试话术**：
> "写前预览的核心是 snapshot 机制：生成预览时给每个目标文件算 SHA256 指纹存下来，用户确认后真正写入前再算一次当前指纹，不一致就说明文件被外部改过，直接拒绝。这防止了 Agent 拿着旧状态覆盖用户在编辑器里的新修改。目录删除还会递归算整个目录树的哈希。"

## 九、Task Plan 任务计划

### 9.1 数据模型

```python
@dataclass(frozen=True)  # 不可变！每次修改产生新对象
class Task:
    id: str                              # 任务唯一 ID
    content: str                         # 任务描述
    status: TaskStatus = "pending"       # pending / in_progress / completed / cancelled
    depends_on: tuple[str, ...] = ()     # 依赖哪些任务（DAG 模式）
    owner: str | None = None             # 执行者（主代理/子代理）
    order: int = 0                       # 线性模式下的顺序

@dataclass(frozen=True)
class TaskPlan:
    mode: TaskPlanMode                   # "linear" 线性 / "dag" 有向无环图
    revision: int                        # 版本号，每次修改 +1
    tasks: tuple[Task, ...]              # 任务列表
```

**关键点**：`TaskPlan` 和 `Task` 都是 `frozen=True`（不可变）。每次修改都产生一个**新的 plan 对象**，revision +1。这是函数式编程的思路，保证历史状态不可篡改。

### 9.2 Revision 链校验 —— 乐观并发控制

这是整个模块最核心的设计，完整链路分四步：

#### 第一步：修改时必须带 expected_revision

```python
def update_tasks(*, plan, expected_revision, updates):
    _require_revision(expected_revision, plan.revision)  # 乐观锁检查
    candidate = TaskPlan(
        mode=plan.mode,
        revision=plan.revision + 1,   # 新版本号 = 旧版本 +1
        tasks=...,
    )

def _require_revision(expected, actual):
    if expected != actual:
        raise TaskPlanRevisionConflict(expected=expected, actual=actual)
```

**乐观并发控制**：你修改前说"我基于 revision=3 改的"，系统检查当前是不是 revision=3。如果别人已经改成 revision=4 了，说明你的修改基于旧版本，直接拒绝，让你重新读最新版本再改。

#### 第二步：写入事件时记录 revision 链

```python
def _finish(self, *, operation, previous_revision, result):
    if result.changed:
        self._writer.append_task_plan_updated(
            previous_revision=previous_revision,   # 改之前的版本号
            operation=operation,
            changes=result.changes,
            snapshot=result.plan,                  # 改之后的完整 plan（含新 revision）
        )
```

#### 第三步：回放时校验 revision 链连续性

```python
def _apply_task_plan_payload(self, view, event):
    previous_revision = event.payload.get("previous_revision")
    revision = event.payload.get("revision")

    # 类型校验（bool 不算 int！）
    if not isinstance(previous_revision, int) or not isinstance(revision, int):
        raise SessionStoreCorruptError(...)

    # 当前 plan 的版本号
    expected_previous = view.task_plan.revision if view.task_plan is not None else 0

    # 链校验：事件里的 previous_revision 必须等于当前 plan 的 revision
    if previous_revision != expected_previous:
        raise SessionStoreCorruptError(...)

    # 链校验：新 revision 必须 = previous_revision + 1
    if revision != previous_revision + 1:
        raise SessionStoreCorruptError(...)

    # 链校验：事件里 snapshot 的 revision 必须等于事件声明的 revision
    if revision != plan.revision:
        raise SessionStoreCorruptError(...)

    view.task_plan = plan  # 校验通过才应用
```

**正常的 revision 链示例**：
```
事件 1: create tasks -> previous=0, revision=1  (plan 从无到有)
事件 2: update task A -> previous=1, revision=2
事件 3: update task B -> previous=2, revision=3
```

如果回放时发现事件 2 写的是 `previous=1, revision=5`（跳号了），或者事件 3 的 `previous=1`（不等于当前的 2），直接报 `SessionStoreCorruptError`——说明事件日志被篡改或损坏了。

#### 第四步：双重锁保证并发安全

```python
@contextmanager
def _mutation_lock(self):
    # 线程锁：同一进程内多线程互斥
    thread_lock = _THREAD_LOCKS.setdefault(session_key, threading.RLock())

    # 文件锁（portalocker）：跨进程互斥
    digest = hashlib.sha256(session_key.encode()).hexdigest()
    lock_path = lock_dir / f"task-plan-{digest}.lock"

    with thread_lock, portalocker.Lock(lock_path, mode="a+b", flags=portalocker.LOCK_EX):
        yield
```

**两层锁**：
- **线程锁**（`threading.RLock`）：防止同一进程内多个线程同时改
- **文件锁**（`portalocker.Lock`，排他锁）：防止不同进程（比如主 Agent 和后台子 Agent）同时改

加锁后，在锁内重新从 JSONL 回放最新状态，再做修改。这样保证你拿到的一定是最新版本，不会基于旧状态改。

### 9.3 三种修改操作

| 操作 | 函数 | 能改什么 |
|------|------|---------|
| **create** | `create_tasks()` | 创建新 plan，或追加新任务 |
| **update** | `update_tasks()` | 改状态（pending->in_progress->completed）、owner、依赖关系 |
| **revise** | `revise_tasks()` | 改任务内容（description） |

每个操作都是**纯函数**：输入旧 plan + 参数，输出新 plan + changes，不修改任何外部状态。

### 9.4 校验规则

每次产生新 plan 后都要过 `validate_plan()`：
1. 任务 ID 唯一
2. 不能依赖自己
3. 不能依赖不存在的任务
4. 依赖不能重复
5. DAG 不能有环（拓扑排序，排不出来就是有环）
6. 线性模式最多一个 in_progress
7. in_progress 的任务必须所有依赖都 completed

### 9.5 投影

`project_plan()` 把内部 plan 转成给模型看的视图，包含：
- `mode`：linear / dag
- `revision`：当前版本号
- `ready_task_ids`：可以开始做的任务（依赖都完成了）
- `blocked_task_ids`：被依赖阻塞的任务
- `topological_levels`：拓扑排序层级
- `tasks`：任务列表

模型看到 `ready_task_ids` 就知道现在该做哪个任务，不会乱序。

**面试话术**：
> "任务计划模块用的是乐观并发控制。TaskPlan 是不可变对象，每次修改产生新对象，revision +1。修改时必须传 expected_revision，和当前版本比对，不一致就抛 RevisionConflict 拒绝——这防止了基于旧状态的并发覆盖。写入 JSONL 时同时记录 previous_revision 和新 revision，回放时校验链的连续性（previous 必须等于当前版本，新 revision 必须等于 previous+1），断了就说明日志损坏。再加线程锁和文件锁双重互斥，保证主 Agent 和后台子 Agent 不会同时改。校验层面还做了 DAG 无环、依赖完整性、线性模式单 in_progress 等规则。"

## 十、Subagent 子代理

### 10.1 设计目标

主 Agent 可以把任务派发给子 Agent，子 Agent 在独立会话里跑，结果回传给主 Agent。支持四种角色：

| 角色 | 定位 | 可用工具 | 后台执行 | Worktree 隔离 |
|------|------|---------|---------|-------------|
| **researcher** | 只读代码库探索、证据收集 | ls/view/grep/glob/tree/read_multi/git_*/diagnostics/think/retrieve_archive | 否 | 否 |
| **reviewer** | 只读审查 diff、调用点、风险 | view/grep/git_status/git_diff/git_log/read_multi/think/retrieve_archive | 否 | 否 |
| **tester** | 验证导向，可执行诊断和命令 | 只读工具 + shell + python_exec | 是 | 否 |
| **coder** | 实现工作 | tester 工具 + write/edit/delete/apply_patch | 是 | **是** |

### 10.2 关键设计约束

1. **子 Agent 没有 delegate 工具**：防止递归派发子 Agent（`tools_for_role()` 里明确排除 `"delegate"`）
2. **独立会话**：每个子 Agent 有全新的 `session_id`，metadata 里标记 `parent_session_id`、`delegate_role`、`delegate_task`
3. **角色独立预算**：不同角色有不同的工具轮次/调用次数/超时限制（researcher 16 轮，coder 40 轮）
4. **前台执行只返回精简摘要**：不把子 Agent 的完整对话历史灌给主 Agent，只返回最终 summary

### 10.3 Coder 角色的 Worktree 隔离

后台运行的 coder 角色必须在 **git worktree** 隔离中执行。核心流程：

1. `WorktreeManager.create(session_id)` 创建独立 git worktree
2. 子 Agent 的 `PermissionManager` 的 `project_root` 指向 worktree 路径，所有路径/shell/git 决策都基于隔离树
3. `SandboxAccess` 模式为 `PROJECT`，物理上限制只能操作 worktree 内文件
4. 子 Agent 的工具全部重建（不复用父 Agent 的工具实例），内部路径沙箱指向 worktree
5. 后台隔离 coder 没有交互用户，禁用写前预览确认（否则会死锁），worktree diff 由父 Agent 审查
6. 跑完后 `manager.diff(worktree)` 计算 worktree 相对于父分支的 diff
7. **不自动合并**：worktree 保留在原地，diff 摘要返回给父 Agent，由父 Agent（或用户）决定是否合并

子 Agent 的 prompt 里明确告知："You are running inside an ISOLATED git worktree... Do not attempt to merge or push."

### 10.4 子 Agent 的权限模式

隔离 coder 使用 `AGGRESSIVE` 权限模式 + 预授权：
- 预授权：worktree 内的 WRITE_PATH 和 DELETE_PATH 自动 allow（因为有 worktree 物理隔离兜底）
- 但敏感路径、危险 shell 命令仍然需要确认（确认会暂停后台任务，而不是逃逸沙箱）
- 全新的 GrantStore，不继承父 Agent 的授权

**面试话术**：
> "子代理通过 delegate 工具调用，支持 researcher/reviewer/tester/coder 四种角色，每种角色有独立的工具白名单和资源预算。子代理没有 delegate 工具，防止递归。关键设计是后台 coder 角色必须在 git worktree 隔离里跑——工具的路径沙箱、PermissionManager 的 project_root 全部指向 worktree，物理上碰不到父工作区。跑完不自动合并，把 diff 摘要返回给主 Agent 审查。子代理有独立的 session_id，metadata 里记录父子关系。"

## 十一、Background 后台任务

### 11.1 设计目标

模型可以给工具调用加 `run_in_background=true`，工具在后台线程跑，主循环不等它，先返回占位符结果，后台跑完后通过 `<task_notification>` 事件通知主 Agent。

### 11.2 核心协议约束

```
后台执行 != 让原始 tool_call 悬空
  ↓
原始 tool_call_id 必须立刻得到一条占位 tool_result（由 ToolExecutor 写入）
  ↓
真正的完成结果稍后作为独立的 <task_notification> 用户消息注入
  ↓
绝不会再产生第二条同 id 的 tool_result
```

这个设计保证了 provider 历史里的 `tool_call -> tool_result` 配对永远合法，不会出现"调用了工具但没有结果"的非法序列。

### 11.3 支持后台的工具白名单

```python
DEFAULT_BACKGROUND_TOOL_NAMES = frozenset({
    # 只读探查
    "ls", "view", "grep", "glob", "tree", "read_multi",
    "git_status", "git_diff", "git_log", "diagnostics",
    # 已做权限预检的执行/网络工具
    "shell", "python_exec", "fetch", "web_search",
    # 子代理
    "delegate",
})
```

**刻意排除**：TaskPlan 写入工具、`task_boundary`/`ask_user`（控制面）、全部写入类工具（要等 worktree 隔离），避免后台任务在没有安全边界时改动主工作区或伪造用户交互。

### 11.4 控制面字段

工具的 schema 会被动态增强三个控制字段（`with_background_controls()`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `run_in_background` | boolean | true 则异步后台执行 |
| `background_label` | string | 可选标签，用于状态识别 |
| `task_id` | string | 可选，关联 TaskPlan 任务 ID，成功完成后自动推进该任务 |

执行前 `strip_background_controls()` 把这三个字段剥掉，不传给真正的工具执行函数。

### 11.5 后台任务管理器

`BackgroundJobManager` 是内存态管理器：
- 用 `ThreadPoolExecutor(max_workers=4)` 跑同步工具执行函数
- 任务 ID 递增且确定（`bg_0001`、`bg_0002`...）
- 并发上限 `max_jobs=8`，满了抛 `BackgroundCapacityError`
- 完成的任务进入 `_completed` 队列，等 AgentLoop 在下次 provider 请求前收集

### 11.6 完成通知的注入时机

**关键设计**：后台任务的完成回调（包括 TaskPlan 状态更新）不在 worker 线程里执行，而是在 `collect_completed()` 时（AgentLoop 主线程、序列化的消费点）执行：

```python
def collect_completed(self, *, session_id=None):
    with self._lock:
        jobs = [...]  # 从 _completed 队列取出
    notifications = []
    for job in jobs:
        self._finalize_task_plan_completion(job)  # 在这里执行 TaskPlan 完成回调
        notifications.append(self._notification_for(job))
    return notifications
```

这样保证 TaskPlan 的 revision 更新不会和正常的会话事件写入产生竞态。

通知渲染成 `<task_notification>` XML 格式注入模型，包含：job_id、tool_name、task_id、observed_revision、task_plan_completion、status、summary。

### 11.7 与 TaskPlan 的联动

后台任务可以绑定 `task_id`，完成后自动把对应任务标记为 completed：
- 启动时记录 `observed_revision`（当前 TaskPlan 的版本号）
- 完成时用 `expected_revision=observed_revision` 调用 `task_update`，带乐观锁
- 如果 revision 冲突（期间任务被改过），重试最多 3 次
- 结果写入 notification 的 `task_plan_completion` 字段

### 11.8 取消机制

- 还没开始执行：直接 `future.cancel()`，标记 cancelled 并产出通知
- 已在运行：设置协作取消 token（`CancellationToken`），能否真正停下取决于工具是否检查取消点

**面试话术**：
> "后台任务的核心协议是：原始 tool_call 立刻得到占位 tool_result（保证 provider 历史合法），真正结果稍后作为独立的 `<task_notification>` 用户消息注入，绝不产生第二条同 id 的 tool_result。只有白名单工具（只读+已预检的执行工具+delegate）支持后台，写入类工具排除。后台任务用 ThreadPoolExecutor 跑，并发上限 8。完成回调不在 worker 线程执行，而是在 AgentLoop 主线程的 collect_completed 消费点执行，避免和会话事件写入竞态。后台任务可以绑定 TaskPlan 的 task_id，完成后自动推进任务状态，带乐观锁重试。"

## 十二、MCP 工具集成

### 12.1 MCP 是什么

MCP（Model Context Protocol）是 Anthropic 提出的工具调用标准协议，让 Agent 可以接入外部 MCP 服务器提供的工具，而不需要为每个工具写专门的适配器。

### 12.2 架构设计

```
McpManager（mcp/manager.py）
  ├── 守护线程运行独立 asyncio event_loop
  ├── 管理多个 MCP 服务器连接（本地 stdio / 远程 SSE）
  ├── 连接后获取工具目录（list_tools）
  └── 提供同步调用入口 call_tool()
```

**异步转同步**：MCP SDK 是异步的，但 AgentLoop 是同步的。`McpManager` 在守护线程里跑独立的 `asyncio event_loop`，通过 `asyncio.run_coroutine_threadsafe()` 把协程提交到那个 loop，主线程用 `future.result()` 等待结果。

### 12.3 连接管理

- `connect_all_in_background()`：后台并行连接，避免 MCP 启动阻塞 TUI 首帧
- 每个服务器独立连接，单个失败不影响其他
- 重试 3 次，间隔 1 秒
- `reconnect()`：支持单个或全部重连
- `close()`：断开所有连接并停止事件循环（可重复调用）

### 12.4 工具发现与激活 —— 关键设计

**不是所有 MCP 工具默认暴露给模型**。原因：MCP 服务器可能有很多工具，全部塞进模型的 tool schema 会占用大量上下文 token。

设计了**按需搜索激活**机制：

1. 初始时，模型只看到一个 `mcp_tool_search` 工具
2. 模型需要某个外部能力时，调用 `mcp_tool_search(query="数据库查询")`
3. 本地搜索算法（`search_mcp_tools()`）对所有已连接 MCP 服务器的工具做关键词匹配打分：
   - 工具名完全匹配 → 10000 分
   - 工具名 token 匹配 → 100 分/token
   - 服务器名 token 匹配 → 20 分/token
   - 描述 token 匹配 → 1 分/token
4. 返回最多 8 个匹配工具，这些工具的 schema **在当前用户轮次内**被激活，模型可以直接调用
5. MCP 工具名以 `mcp__` 前缀注册（如 `mcp__postgres__query`）

### 12.5 权限控制

MCP 工具调用走同一套权限预检：
- `PermissionAction.MCP_TOOL` → 默认 `ask`
- 用户可以选择 allow once / allow always
- 配置文件里可以设置 `allowed_tools` 白名单（支持 fnmatch 通配符），白名单内的工具连接后直接可用

### 12.6 配置

支持两种服务器类型：
- **本地 stdio**：`McpLocalServerConfig`（command + args + env）
- **远程 SSE**：`McpRemoteServerConfig`（url + headers + bearer_token_env_var）

配置支持环境变量占位符（`{env:VAR_NAME}`），运行时解析。

**面试话术**：

## 十四、Harbor 隔离评测

### 14.1 Harbor 是什么

Harbor 是一个**基于 Docker 的 Coding Agent 评测运行时**（`pip install harbor==0.18.0`）。一个 Harbor 数据集是一组任务，每个任务提供：指令、隔离执行环境、verifier（判分器）。

### 14.2 工作流程

```
Harbor 数据集（如 Aider Polyglot 225 题）
  ↓ 每道题
启动一个全新 Docker 容器（隔离环境）
  ↓ 容器内
把目标代码仓库拷贝进去 -> 启动 TraceCoder Agent（非交互模式 --benchmark）
  ↓ Agent 执行完
调用 verifier（跑 pytest / 判分脚本）-> 写 reward.txt
  ↓
收集结果 -> 销毁容器 -> 下一题
```

### 14.3 TraceCoder 的适配层

`benchmark/harbor/agent.py` 里的 `TraceCoderHarborAgent`：
- 每个任务只拷贝 `pyproject.toml`、`README.md`、`tracecoder/` 源码
- **不拷贝** `.git`、`.venv`、本地 session、`.env` 等工作区文件
- Agent 以 `--benchmark` 非交互模式运行，权限模式为 `BYPASS`（评测环境不需要用户确认）
- 支持 `--max-tool-rounds`、`--model` 等参数覆盖
- 支持 Aider Polyglot 的 feedback plugin（允许 verifier 给一次反馈修复机会）

### 14.4 评测结果

对标 Aider Polyglot 225 题：
- 明确判分任务：213 / 221 通过，**96.38%** reward-only pass@1
- Harbor 端到端平均得分：**94.67%**

结果包路径：`benchmark/runs/harbor/aider-polyglot-feedback-retry-20260726/2026-07-26__12-07-27/`

### 14.5 为什么不用本机直接跑评测

| 本机跑 | Harbor 容器跑 |
|-------|-------------|
| Agent 可能删改你本机代码 | 容器销毁就没了，宿主机不受影响 |
| 上一题的残留文件影响下一题 | 每题全新容器，环境干净 |
| 本机装的依赖/环境变量干扰结果 | 容器内依赖统一，结果可复现 |
| 225 题串行跑很慢 | 支持并发（`-n 2`），多容器同时跑 |

**面试话术**：
> "Harbor 是一个基于 Docker 的 Coding Agent 评测运行时。我们写了 TraceCoderHarborAgent 适配器，每个评测任务在独立容器里运行，Agent 只接触容器内的代码副本，跑完 verifier 判分后销毁容器。这样保证 225 道题的评测结果干净、可复现，不会被本机环境污染。对标 Aider Polyglot 拿到 96.38% 通过率，这个分数的可信度就建立在隔离评测之上。"

## 十六、核心概念解释

### 16.1 ThreadPoolExecutor 并行

**是什么**：Python 标准库 `concurrent.futures` 里的线程池。把多个独立任务丢进线程池同时跑，不用一个一个等。

**项目里用在哪**：
- 只读工具的并行执行（`tool_execution.py`）：模型一轮返回多个只读工具调用（如同时 grep 三个关键词），并行执行减少等待
- 后台任务执行（`background.py`）：`ThreadPoolExecutor(max_workers=4)` 跑后台工具

**为什么不用多进程**：这些工具主要是 IO 密集（读文件、跑 git 命令），Python 线程在 IO 等待时会释放 GIL，线程池足够了，而且线程间共享内存比进程方便。

### 16.2 SHA256 哈希

**是什么**：一种密码学哈希函数，给任意长度的输入算出一个固定 256 位（64 个十六进制字符）的"指纹"。输入改一个字符，输出就完全不同。

**三岁小孩版**：就像给文件拍一个"数字指纹"，文件内容变了，指纹就变了。你不用对比整个文件，只看指纹一不一样就知道文件有没有被改过。

**项目里用在哪**：
1. **写前预览的快照校验**：生成预览时算一次文件 SHA256，用户确认后真正写入前再算一次，两次不一样就拒绝
2. **归档的内容寻址**：`archive_id = ar_{sha256[:32]}`，相同内容永远得到相同 ID，重复归档是 no-op
3. **归档完整性校验**：读取归档时重新算 SHA256，和存的 metadata 对比，不一致说明文件损坏
4. **工具结果去重**：用内容 SHA256 判断两个工具结果是不是完全一样，一样的标记为 DUPLICATE

### 16.3 Snapshot（快照）

**是什么**：在某个时间点，把目标文件的状态"拍一张照片"存下来。这里的快照就是 `(文件路径, 当前 SHA256 哈希)` 这个元组。

**为什么需要**：Agent 生成预览和用户点确认之间可能隔了几秒，这期间用户可能在编辑器里手动改了文件。snapshot 防止 Agent 拿着旧状态覆盖用户的新修改——确认后先检查文件指纹变没变，变了就拒绝。

## 十七、面试高频问答

### Q1：append-only JSONL 崩溃了怎么办？

> JSONL 用追加模式写入，每行一个完整 JSON 事件。崩溃最多损坏最后一行（写了一半），前面的历史事件完好。恢复时逐行 `json.loads`，坏行可以跳过或报错。我们还有 SessionIndex 做索引，SessionCatalog 标记 session 状态（corrupt/empty/usable），恢复前先 validate_session_schema 校验 schema 版本。

### Q2：L1-L4 压缩具体每级做什么？

> - **L1**：裁剪旧任务的普通对话文本（不碰带 tool_call 的消息，不破坏工具事务）
> - **L2**：对已消费的工具结果按内容类型（JSON/HTML/diff/源码/构建输出等）路由压缩，原始内容归档留 archive_id 可找回
> - **L3**：把重复/过期/被取代/超大的工具结果替换成 480 字符占位符，只留工具名/状态/生命周期/摘要/错误信息，原始内容归档可检索
> - **L4**：调 LLM 生成旧历史摘要，创建 checkpoint，checkpoint 之后的消息作为 recent tail 保留
>
> L1-L3 不调模型，快且确定；L4 才调模型。每级后都校验 tool_call/tool_result 序列合法性。

### Q3：L3 不调大模型，怎么生成摘要？

> L3 的"摘要"不是 LLM 生成的，是从工具结果的结构化 metadata 里用固定模板拼出来的纯文本。工具名、成功/失败状态、生命周期分类（过期/被取代/重复）、原始 token 数都是工具执行时就记录的原始数据，默认摘要就是 `f"Large {tool_name} result ({tokens} tokens)"`。错误信息直接取工具执行时记录的 error 字段。整个占位符硬限制 480 字符。原始内容存在内容寻址的归档里，模型需要时调 retrieve_archive 按需取回。

### Q4：怎么防止 Agent 乱改本地代码？

> 三层防护：
> 1. **路径沙箱**：PathSandbox 限制只能操作项目根目录，删除根外路径直接 deny
> 2. **权限策略**：allow/ask/deny 三级，敏感文件（.env/.pem/.key/.git）和敏感环境变量硬拒绝
> 3. **写前预览+快照校验**：write/edit/apply_patch/delete 执行前先生成 unified diff 预览和 SHA256 快照，用户确认后真正执行前再算一次哈希，文件被外部改过就拒绝执行

### Q5：工具调用序列怎么保证合法？

> 两个层面：
> 1. **写入顺序硬约束**：loop.py 里必须先 append_assistant_response(response)（含 tool_calls），再执行工具并 append_tool_result，保证 provider 看到的永远是 assistant->tool 的合法序列
> 2. **压缩后校验**：L4 checkpoint 提交后，ContextBuilder 投影时会检查 InvalidToolCallSequenceError，有 tool_call 没配对 tool_result 就报错
> 3. **中断修复**：每次 provider 请求前检查悬挂的 tool_call，补写 interrupted 结果

### Q6：会话中断后怎么恢复？

> 所有事件都在 JSONL 里。恢复时 rebuild_session_view() 逐事件回放，重建内存中的 SessionView。如果上次卡在权限确认，restore_pending_permission_execution() 从 JSONL 里恢复 pending_permission_execution 状态（包括原始 tool_call 的深拷贝，不信任 UI 回传的参数），直接继续等用户确认，不需要重新走一遍模型。

### Q7：长任务上下文爆炸怎么处理？

> 双水位线触发（high_watermark/low_watermark），超过高水位自动压缩到低水位。压缩走 L1->L2->L3->L4 逐级升级，每级后检查是否达标。还有熔断器（连续失败就暂停自动压缩）、无效果去重（相同 fingerprint 不重复压缩）。Provider 报 context 过长时还会触发 PROMPT_TOO_LONG 紧急压缩后重试。

### Q8：task_plan 的 revision 链是怎么回事？

> 乐观并发控制。TaskPlan 是不可变对象，每次修改产生新对象，revision +1。修改时必须传 expected_revision，和当前版本比对，不一致就抛 RevisionConflict 拒绝。写入 JSONL 时同时记录 previous_revision 和新 revision，回放时校验链的连续性（previous 必须等于当前版本，新 revision 必须等于 previous+1），断了就说明日志损坏。再加线程锁和文件锁双重互斥，保证主 Agent 和后台子 Agent 不会同时改。

### Q9：子代理和主代理怎么隔离的？

> 子代理有独立的 session_id，工具按角色白名单限制，没有 delegate 工具防止递归。关键是后台 coder 角色必须在 git worktree 隔离里执行——工具的路径沙箱、PermissionManager 的 project_root 全部指向 worktree 路径，SandboxAccess 模式为 PROJECT 物理限制，碰不到父工作区。跑完不自动合并，diff 摘要返回给主 Agent 审查。

### Q10：后台任务怎么保证不破坏工具调用序列？

> 核心协议：原始 tool_call_id 立刻得到一条占位 tool_result（闭合 provider 历史里的 tool_call），真正的完成结果稍后作为独立的 `<task_notification>` 用户消息注入，绝不会再产生第二条同 id 的 tool_result。这样 provider 看到的永远是合法的 tool_call->tool_result 配对。

### Q11：MCP 工具为什么不直接全暴露给模型？

> MCP 服务器可能有很多工具，全部塞进模型的 tool schema 会占用大量上下文 token。我们设计了按需搜索激活：模型初始只看到 mcp_tool_search 工具，需要外部能力时搜索关键词，本地打分匹配后最多激活 8 个工具在当前轮次可用。

### Q12：评测怎么做的？

> Harbor Docker 容器隔离，每题独立环境，verifier 判分，对标 Aider Polyglot 96.38%。

### Q13：多模型怎么支持？

> ChatProvider 抽象接口，OpenAI 兼容/Anthropic 两套实现，环境变量切换。

### Q14：工具调用并行吗？

> 只读工具 ThreadPoolExecutor 并行，写操作串行。

### Q15：项目最大的难点/亮点是什么？

> 选一个你最熟的讲（推荐上下文压缩 L1-L4 或写前快照校验）。
